---
name: factory-ship
description: Ship a factory job's change - commit, push and open the draft PR with testing proof, then later mark it ready, triage CI, rebase, post approved review replies or merge, each under its approved gate. Use when a factory lead reaches its shipper, commit-on-main or pr step, or a "From factory" message names CI, a conflict, replies or a merge.
---

You ship the job you lead. Approval of Gate 2 is Stef's permission to commit and push this change, nothing else. Do one mode and stop: CI, reviews and conflicts come back later as factory messages, so never wait on or babysit a PR. A hook enforces every gate below.

- **ship** (default): load `pr-desc` and `p-dev:open-pr`. Commit the worktree changes in the repo's style plus the commit attribution lines from your system context, push the branch, open the PR as a draft (or update it), then run `factory pr add <pr url>` from inside the workspace. The body is pr-desc's: the repo template, one or two lines, the Productive task (`factory job task`) linked by id, and a **Testing** section per `/Users/stef/dev/productive/work/knowledge/processes/testing-proof.md`, built from your coder and tester reports: what was run and what was observed, reaching every change the PR makes. Anything beyond a small change goes into one HTML report uploaded with `tb-backyard share upload`, linked from that section. Specs alone are not proof of a behaviour change; a run with no live evidence for one still ships the draft and says so at the ready gate. A PR touching only specs, docs or other exempt files says `Testing: n/a — <why>`. Flag and deploy caveats go in a **Rollout** section. The Productive task carries the intent, the why and the spec (its specs-repo link, or the job's `spec.md` uploaded with `tb-backyard share upload` after `factory file cat spec.md > /tmp/<slug>-spec.md`); add what is missing, keep what is there, and add one unassigned `PR: <url>` TODO. No reviewers, never ready. No task recorded and Stef did not choose none: ask him at the gate first. An existing PR in the brief: push to its branch and refresh its Testing section, never a second PR. For each thread in the job's `threads.md` (`factory file cat threads.md`) the job addressed, draft a reply.
- **commit-on-main**: commit on the default branch, no PR.
- **ready**: only under an approved ready gate, `gh pr ready <N>` (skip when already ready), `gh pr edit <N> --add-reviewer <logins>` only for reviewers Stef named, then one `PR: <url>` TODO per person `gh pr view <N> --json reviewRequests` now lists on the task assigned to them in place of the unassigned one, and the task's status set to Peer Review. Never change the task's assignee; it stays on the developer.
- **ci triage**: load `tb-sem`. Classify each failing check before any retry. A flake gets one rerun. A failure in the diff is a fix round: plan `coder review` rows and fix it. A failure in code the diff never touched means a stale base: rebase and push.
- **rebase**: rebase on the base branch and push with `--force-with-lease <remote> <branch>`. A conflict you cannot resolve without guessing: bring the hunks to Stef.
- **post replies**: only under an approved replies gate; post exactly the approved drafts, one per thread, paired by the thread's `path:line` and root comment id, never by list position. Then re-list the PR's review comments and check each reply's `in_reply_to_id` and body against its draft; delete and repost any mismatch.
- **merge**: only under an approved merge gate: `gh pr merge <N> --squash --subject "<PR title> (#<N>)" --body "Task: <productive task id>" --match-head-commit <head sha>`. GitHub refuses a merge while any review thread is unresolved, bots' included: check first and bring the open threads to Stef. With a task the body is always `Task: <id>`; "Stef chose no task" merges with no `--body`.

Record the step with the full PR URL and head SHA in the note.
